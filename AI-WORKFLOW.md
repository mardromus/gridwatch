# AI Workflow

## Tools and division of work

GitHub Copilot was used as an implementation partner inside VS Code for problem
decomposition, code generation, tests, CSS, Docker files, and documentation. I
kept ownership of the physical model, confidence policy, scope, and acceptance
checks. The final repository is approximately 95% AI-generated by line count;
that number includes tests and docs and is not a claim about decision ownership.

Delegated nearly wholesale:

- React/TypeScript component and CSS implementation after the information
  hierarchy was specified;
- FastAPI request/response plumbing;
- repetitive seed generation, Docker, and documentation structure; and
- unit-test scaffolding.

Kept under explicit human/product control:

- why a live descendant invalidates a line fault;
- recorded versus inferred topology behavior;
- the decision to group inferred candidates rather than overclaim precision;
- the causal-fit formula and the policy that telemetry may overrule a schedule;
- workflow semantics around `resolved`, `verified`, and `closed`; and
- the boundary that prevents the LLM from localizing or mutating tickets.

## Where AI output was wrong

### 1. One fault became twelve incidents

The first inferred-graph implementation passed small unit fixtures. In the real
2,160-pole browser flow, one physical span injection produced 12 candidate
frontiers because geometric parents did not match the simulator's hidden true
tree. The UI check caught it. I rejected the apparent "working" result, added a
regression test, and changed unknown-topology policy to one low-confidence zone
with multiple candidate boundaries.

### 2. Default simulator target was not a span

The generated target used `pole_ids[len/3]`, which landed on the root of the
second arm and had no parent. Engine tests raised `No available target for span`.
The fix selects a non-root pole with descendants and later excludes transformers
already hosting an active simulated fault.

### 3. Optional server extras broke Windows ARM

The generated requirement `uvicorn[standard]` pulled `httptools`, which failed
to link against `MSVCRT.lib` on Windows ARM. The native extras add no value to
this polling demo. I removed them, recreated the Python 3.12 environment, and
reran the API smoke flow with plain Uvicorn.

### 4. A benchmark call was syntactically plausible but wrong

AI passed a JSON dictionary as a positional `TestClient.post` argument. Runtime
validation raised a `TypeError`. It was corrected to `json=...` before any
performance number was documented. The final document labels the result a local
microbenchmark rather than a production p95 claim.

## Strong prompts / session excerpts

The most useful instructions were constraint-heavy and falsifiable:

> Implement the radial-network frontier as a pure testable function. One dark
> subtree must create one span incident; a dark pole with a live descendant must
> be sensor noise; missing boundary devices must produce a range; inferred edges
> must lower confidence.

> Build the console around the operator's 2 a.m. decision order: severity and
> exact location first, confidence and evidence second, workflow actions third.
> Manual closure must not exist.

> The LLM may summarize and translate only a locked incident JSON object. It may
> include the deterministic causal fingerprint, but may not choose the fault,
> change confidence, assign a crew, or mutate status. Validate its schema and
> provide a no-key fallback.

The shipped UI shows that deterministic fallback immediately. A model call is
made only when an operator asks to refine or translate it, keeping dispatch
usable without a key and preventing telemetry volume from creating model cost.

Those prompts worked because they described observable behavior and forbidden
failure modes, not just framework choices.

## How output was checked

- 29 backend tests cover localization, topology provenance, simultaneous faults,
  sensor noise, evidence-based schedule suppression, planned-window mismatch,
  dirty telemetry, late retries, causal fit, and telemetry-gated closure.
- The production frontend passed TypeScript build and ESLint.
- Browser automation drove inject -> rejected dark-resolution claim -> repair ->
  telemetry-verified/closed, with no manual resolve prerequisite.
- Desktop and 390 px mobile layouts were rendered; a 126 px mobile overflow was
  found and fixed, then measured at zero.
- Browser automation verified a normal span at 100% causal fit and a planned DT
  scope at only 17% signature coverage being correctly escalated.
- A 5,000-message API-path benchmark was run only after the request itself was
  validated.

The Docker image could not be executed because the authoring machine had no
Docker CLI or engine. The public repository was cloned into a fresh directory;
all 28 backend tests, Ruff, npm install, ESLint, and the production frontend
build passed there. Manual Compose verification remains required and is repeated
in deployment documentation rather than silently converted into a claim.
